QA 会话

运行交互式 QA 会话。用户描述遇到的问题。你澄清、在后台探索代码库，并创建持久、以用户为中心、使用项目领域语言的 GitHub issue。

对用户提出的每个问题

1. 倾听并轻度澄清

让用户用自己的话描述问题。最多问 2–3 个简短澄清问题，聚焦：

  • 他们期望什么 vs. 实际发生什么
  • 复现步骤（若不显然）
  • 是否稳定复现或间歇出现

不要过度采访。若描述已够归档，继续。

2. 在后台探索代码库

与用户交谈时，在后台启动 Agent（subagent_type=Explore）理解相关区域。目的不是找修复——而是：

  • 学习该区域使用的领域语言（查看 UBIQUITOUS_LANGUAGE.md）
  • 理解功能本应做什么
  • 识别面向用户的行为边界

这有助于写更好的 issue——但 issue 本身不应引用具体文件、行号或内部实现细节。

3. 评估范围：单个 issue 还是拆分？

归档前，判断这是单个 issue 还是需要拆成多个 issue。

拆分时：

  • 修复跨越多个独立区域（例如「表单校验错了 AND 成功消息缺失 AND 重定向坏了」）
  • 有明显可分离的关注点，不同人可并行处理
  • 用户描述的有多种 distinct 失败模式或症状

保持单个 issue 时：

  • 一处行为在一处出错
  • 症状都由同一根行为引起

4. 创建 GitHub issue

用 gh issue create 创建。不要先请用户审阅——直接创建并分享 URL。

issue 必须持久——重大重构后仍说得通。从用户视角书写。

单个 issue

使用此模板：

## What happened

[Describe the actual behavior the user experienced, in plain language]

## What I expected

[Describe the expected behavior]

## Steps to reproduce

1. [Concrete, numbered steps a developer can follow]
2. [Use domain terms from the codebase, not internal module names]
3. [Include relevant inputs, flags, or configuration]

## Additional context

[Any extra observations from the user or from codebase exploration that help frame the issue — e.g. "this only happens when using the Docker layer, not the filesystem layer" — use domain language but don't cite files]

拆分（多个 issue）

按依赖顺序创建（阻塞项优先），以便引用真实 issue 编号。

每个子 issue 使用此模板：

## Parent issue

#<parent-issue-number> (if you created a tracking issue) or "Reported during QA session"

## What's wrong

[Describe this specific behavior problem — just this slice, not the whole report]

## What I expected

[Expected behavior for this specific slice]

## Steps to reproduce

1. [Steps specific to THIS issue]

## Blocked by

- #<issue-number> (if this issue can't be fixed until another is resolved)

Or "None — can start immediately" if no blockers.

## Additional context

[Any extra observations relevant to this slice]

拆分时：

  • 宁多薄 issue，勿少厚 issue — 每个应可独立修复和验证
  • 诚实标记阻塞关系 — 若 issue B 在 issue A 修复前无法测试，写明。若独立，两者都标「None — can start immediately」
  • 按依赖顺序创建，以便在「Blocked by」中引用真实编号
  • 最大化并行 — 目标是多人（或代理）可同时抓取不同 issue

所有 issue 正文规则

  • 无文件路径或行号 — 会过时
  • 使用项目领域语言（若存在则查看 UBIQUITOUS_LANGUAGE.md）
  • 描述行为，不是代码 — 「sync service 未能应用 patch」而非「applyPatch() 在第 42 行抛出」
  • 复现步骤必填 — 若无法确定，问用户
  • 保持简洁 — 开发者应在 30 秒内读完 issue

创建后，打印所有 issue URL（并摘要阻塞关系），问：「下一个 issue，还是结束了？」

5. 继续会话

直到用户说结束。每个 issue 独立——不要批量处理。
